# spec-lint

> PRD / Spec 的质量门禁——"需求文档的单元测试"。

生成式 AI 让写一份*漂亮*的需求文档成本趋近于零，瓶颈从"生产"转移到了"判断"：目标不可度量、证据缺失、范围悄悄膨胀、内部自相矛盾的 Spec 大量流入研发，带来返工。

`spec-lint` 是一个 **Codex 技能（Skill）**：对需求文档做 linter 式评审，输出**带原文引用**的质疑清单。它不评价产品方向对错，只保证决策依据是显形的、可度量的、自洽的。

**只评审，不代写、不改写、不评分。**

## 为什么需要它

代码世界有两条腿：生成（Copilot）+ 验证（linter、类型检查、测试）。Spec 世界目前只有一条腿——生成侧工具（spec-kit、OpenSpec、各种 PRD 模板）极度丰富，验证侧只有结构校验（文件在不在、格式对不对）和"把 PRD 丢给模型点评"式的正确废话。

`spec-lint` 补的是验证侧：像 ESLint 一样，每条问题有规则 ID、有严重度、有精确到行的证据，且**规则可关闭**——误报一次就能永久关掉那条规则，而不是卸载整个工具。

## 工作原理

两步检查，合并出报告：

1. **机械检查**（`scripts/check_mechanical.py`，确定性、零误报）：扫描占位符（TBD/待定）、模糊形容词、弱模态词（尽量/原则上）、"等"式开放列举、"和/或"、含数字行，输出带行号的 JSON 证据。
2. **语义检查**（模型按 `references/rules.md` 逐条判定）：成功指标缺失、指标不可测、内部矛盾、非功能空白、安全合规遗漏等需要理解上下文的规则。机械检查结果作为证据输入，不替代语义判断。

铁律：**每条 finding 必须逐字引用原文并标注位置**；拿不准的问题降级或归入「需人工确认」，不混入硬伤——linter 的生命线是精度，误报比漏报更致命。

## 安装

```bash
git clone https://github.com/allanzhang/spec-lint
cp -R spec-lint ~/.codex/skills/spec-lint
```

重启 Codex 后技能生效。其他支持 SKILL.md 约定的 agent（Claude Code 等）同理放入其技能目录。

## 使用

对 Codex 说："用 spec-lint 评审这份文档"，输入支持：

- **本地文件**：`.md` / `.txt` 直接评审；
- **任意可解析格式**：`.docx` / `.pdf` / `.html` 等先转换为 Markdown 再评审（报告注明"基于转换文本，表格/排版可能有损耗"）；
- **直接粘贴**的文本；
- **飞书文档链接**：可选分支，通过 lark-doc 技能读取；不可用时退回"请导出 Markdown/Word"，主流程不依赖任何外部集成。

报告示例（节选）：

```markdown
# Spec 评审报告：智能推送中心 PRD

## 摘要
- 🔴 5 项必须回答 · 🟡 8 项建议补充 · 🔵 3 项表述问题
- 结论：当前不具备进入研发评审的条件。卡点：成功指标完全不可度量、
  功能范围数量自相矛盾、存在 TBD 未定项。

## 🔴 Blocker
### [B1/B2] 目标与指标全是模糊词，无法判断成败
- 位置：§1 目标（第 7-9 行）
- 原文：「显著提升新用户的上手效率，让首周体验更流畅」
- 问题："显著/流畅"无度量主体，上线后无法判断目标达成没有。
- 请回答：对应的指标是什么？基线值、目标值、采集方式各是什么？
```

Blocker 全部是"请回答"式填空题：作者要么填上答案（Spec 真的变好了），要么显式驳回（说明是有意为之）。两种动作都让 Spec 变强。

## 与 spec-kit / OpenSpec 的关系

不冲突，是上下游：

- **spec-kit / OpenSpec** 是规格驱动*开发流水线*（写 spec → plan → tasks → 代码），住在代码仓库里，只检查自家制品之间的一致性；
- **spec-lint** 是独立*门禁*：任何来源、任何格式的 PRD 都能评审，且检查的是规格与现实之间的接地（可度量、无矛盾、无模糊承诺），不依附任何写作流水线。

典型衔接：PM 在文档里写 PRD → **spec-lint 门禁评审** → 通过后进入 spec-kit/OpenSpec 流水线开发。

## 自进化机制

规则库不靠空想扩充，靠每次评审的反馈闭环：

1. 每份评审报告末尾征求裁决（误报 / 漏报 / 级别调整）；
2. 裁决记入 `references/calibration.md` 校准日志；
3. 规则改动先在工作副本起草，跑 `scripts/selftest.py` 回归（`tests/` 含正反例语料库），用户确认后才发版；
4. 新规则先以低严重度试运行，连续 ≥3 份文档确认有效才升级；高频误报或长期零命中的规则降级或删除。

## 路线图

- **v1.3（当前）**：28 条规则，纯文档分析，零外部依赖；机械检查器已经过 3200+ 行 SaaS PRD + 硬件玩具 PRD 两类语料校准（排除业务状态名、幂等/系列/等价/等我等技术与日常用语误报）；评审反馈经 `references/calibration.md` 日志驱动规则进化。
- **v2（需接数据源）**：
  - D 组 证据溯源："用户强烈要求 X"必须链接到纪要/访谈/数据；证据强度匹配；与历史决策冲突检测（决策图谱）；
  - E 组 影响面：需求波及的模块/埋点/合同承诺；指标对应的埋点采集方案。
- 规则库持续用真实 PRD 校准：误报降级/移除，漏报增补，演变过程见 commit 历史。
