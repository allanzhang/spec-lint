# 评审规则库 v1.4.0

严重度：🔴 Blocker（开发/评审前必须回答）｜🟡 Warning（大概率返工，建议补）｜🔵 Nit（表述问题，顺手改）

每条 finding 必须包含：规则 ID、位置（章节 + 行号/原句）、问题说明、**请作者回答的具体问题**（填空题，不是"建议优化"）。

判定原则：证据不足时降级或归入「需人工确认」；宁可少报，不可错报。

## 规则出处（每条规则末尾标注）

- **[IEEE830]** IEEE 830 软件需求规格质量特性：无歧义、完整、一致、可验证、按重要性/稳定性排序、可追溯。
- **[Clarify]** GitHub spec-kit `/speckit.clarify` 的歧义与覆盖度扫描分类法。
- **[OpenSpec]** OpenSpec 的提案/规格约定（Why/What Changes/Impact、SHALL/MUST 规范式表述、WHEN/THEN 验收场景）。
- **[PRFAQ]** Amazon PR/FAQ 与 Atlassian PRD 框架：问题定义先行、非目标、依赖与发布计划。
- **[Ambiguity]** 需求歧义研究（Berry/Kamsties 等的歧义词典）：模糊形容词与推诿式表述。
- **[经验]** 从返工机理反推、尚待真实语料校准的先验规则。
- **[校准]** 2026-08-27 真实 PRD 语料（SaaS 工程 PRD、IoT 智能硬件 PRD、调研可行性文档四类体裁）评审后新增/修订的规则。

## A. 完整性与结构

### A1 🔴 缺少成功指标 / 验收标准 [IEEE830 可验证]
- 判定：全文没有任何可度量的上线后判断依据（无指标、无目标值、无"验收标准/成功标准"章节）。
- 注意：有"指标"章节但全是模糊词（见 B1/B2）时，A1 与 B1/B2 同时报。
- 请回答：本项目上线后用哪 1-3 个指标判断成功？基线是多少？目标值是多少？数据从哪来？

### A2 🟡 缺少非目标（Non-goals） [PRFAQ]
- 判定：没有明确写出"本期不做什么"。
- 请回答：本期明确不覆盖的场景/平台/用户群是哪些？

### A3 🟡 缺少目标用户定义 [Clarify personas / PRFAQ]
- 判定："用户"一词出现，但全文无用户画像、角色或使用场景定义。
- 请回答：这个功能的主要使用者是谁（角色/场景）？与现有用户群什么关系？

### A4 🟡 缺少边界与异常场景 [Clarify edge cases / IEEE830 完整]
- 判定：只描述主流程，无空状态/加载态、无权限、无失败/超时处理；涉及并发操作时无冲突处理。
- 请回答：数据为空/用户无权限/依赖服务失败/两人同时操作时分别怎么处理？

### A5 🔴 残留未完成痕迹 [Clarify placeholders]
- 判定：TBD、TODO、待定、待补充、待明确、xxx、???、【】、中文尖括号占位等（脚本 A5 规则自动检出）。
- **误报防护（校准）**：业务状态名「待确认」（如订单状态）、UI 术语「骨架占位/占位图/占位提示」、代码示例 `<domain>/<JWT>`、价格示意 `¥xxx` 均**不算**占位。
- 同一行同时命中「待定」与 G1 决策标记（如"审批流待定"）时，按 **G1** 报告，不重复计 A5。
- 请回答：此处待确定的内容是什么？由谁、在什么时间点补齐？

### A6 🟡 需求无优先级 [IEEE830 按重要性排序]
- 判定：需求/功能清单平铺，无 P0/P1、MoSCoW 或任何取舍说明。
- 请回答：如果资源只够做一半，哪些需求可以砍？哪些需求是稳定的、哪些可能变？

### A7 🔴 问题定义缺失 [PRFAQ]
- 判定：文档直接讲方案，没说清"谁、在什么场景下、遇到什么问题、现状有多严重、为什么现在做"。
- 请回答：这个功能解决谁的什么问题？现状数据/证据是什么？不做会怎样？

### A8 🟡 决策无备选 / 取舍记录 [Clarify tradeoffs]
- 判定：结论性方案无论证——没写考虑过哪些备选、为什么否掉。
- 请回答：评估过哪几个方案？选择当前方案的关键取舍是什么？

## B. 可度量性

### B1 🔴 模糊形容词无度量主体 [Ambiguity / Clarify ambiguous adjectives]
- 判定：出现"高效、流畅、显著、大幅、更好、极致、友好、便捷、智能化、一站式、丰富、完善、明显、鲁棒、直观、灵活、可靠、可扩展、无缝、现代化、强大、易用"等词，且上下文无"对谁、在哪个环节、从多少到多少"（脚本 B1 规则提供候选行，需结合上下文确认）。
- 反例（误报防护）：「将首页加载时间从 2.1s 优化到 1.0s」中的"优化"不报——有度量主体。
- 反例（误报防护，校准 v1.4.0）：「显著标识」是 AI 生成内容标识的法定术语，不报；风险叙述中的"显著降低风险"若同句/同段紧跟"降低≠消除/结论以法务意见为准"等自我限定，属定性叙述而非指标断言，不报。
- 请回答：这个词对应的具体指标是什么？当前值和目标值是多少？

### B2 🔴 指标不可测 [IEEE830 可验证]
- 判定：声明了指标（如"提升满意度"），但缺基线、目标值、数据来源三者之一；或指标本身无法采集。
- 请回答：该指标的基线值、目标值、采集方式（埋点/问卷/后台数据）分别是什么？

### B3 🟡 需求不可验收 [OpenSpec WHEN/THEN / IEEE830 可验证]
- 判定：功能需求无法推出"验收时怎么判断做对了"，缺少触发条件 + 预期结果。
- 请回答：这条需求的验收场景是什么？（当 <触发条件> 时，系统应 <可观察的预期结果>）

### B4 🔵 时间承诺无依据 [经验]
- 判定：出现"Q4 上线""两周完成"等时间点，但无依赖说明或粗排期支撑。
- 请回答：这个时间点的前提依赖是什么？谁确认过可行性？

## C. 歧义与自洽

### C1 🔵 术语未定义即使用 / 同概念多名 [Clarify terminology]
- 判定：专有名词、缩写、内部代号首次出现无定义；或同一概念在文中混用多个叫法（如"推送中心/消息平台/通知系统"指同一物）。
- 请回答：这个术语指什么？全文统一用哪个叫法？

### C2 🔴 内部数字 / 说法矛盾 [IEEE830 一致]
- 判定：同一事实在文中两处数字或范围不一致（脚本 C2 规则输出所有含数字的行供交叉核对）。
- 例：前文"覆盖 3 个核心场景"，后文场景清单列出 5 个。
- 请回答：以哪个数字为准？另一处是笔误还是口径不同？

### C3 🟡 "等"式开放列举 [Ambiguity "etc."]
- 判定：需求/范围以"等、等等、之类、诸如此类"收尾（脚本 C3 规则自动检出）。
- **误报防护（校准）**：「幂等」的等字、「等回款/等财务/等通知」的等待义不报；「不等/等价/等号」等固定词不报；法规/公文/通知的**原文直接引语**（成对引号内）中的"等"是引文而非作者的开放列举，不报（脚本按引号掩码排除，引号外的"等"仍为候选）。
- 请回答：除已列出的项，是否还有确定要做的？没有请改为封闭式表述。

### C4 🟡 主语缺失 / 责任悬空 [经验]
- 判定："需要优化推送策略""建议加强引导"——谁做、对谁做、在哪个环节均未说明。
- 请回答：这句话的行动方是谁？在哪个环节做什么动作？

### C5 🔵 否定式需求表述 [经验]
- 判定："不影响现有用户""不改变原有流程"——否定式承诺无法直接验收。
- 请回答：如何验证"不影响"？监控哪些指标、观察多久？

### C6 🟡 弱模态 / 推诿式表述 [Ambiguity "as much as possible" / OpenSpec SHALL]
- 判定："尽量、尽可能、争取、原则上、视情况、酌情、最好能、也许、大概"等（脚本 C6 规则自动检出候选）。规范式需求应是"系统应/必须 <可判定行为>"，弱模态等于没承诺。
- 请回答：这条到底做不做？做的话，可判定的完成标准是什么？

### C7 🔵 "和/或"等逻辑范围歧义 [Ambiguity "and/or"]
- 判定："支持 A 和/或 B"——并列还是可选不明，直接影响开发量和验收口径。
- 请回答：A、B 是都必须做，还是二选一？

## F. 非功能性与上线就绪（v1.1 新增）

### F1 🟡 非功能性需求空白 [Clarify NFR / IEEE830 / Atlassian]
- 判定：全文对性能、可靠性/可用性、安全隐私、合规、可观测性等质量属性无任何声明（并非每项都必须写，但与功能风险相关的维度应有交代）。
- 请回答：这个功能在响应时间、失败恢复、数据保护上分别有什么最低要求？

### F2 🔴 高风险域无安全 / 合规声明 [Clarify security & privacy]
- 判定：功能涉及支付、权限、个人隐私数据，但全文无鉴权、数据保护或合规说明。
- 请回答：涉及哪些敏感数据/权限？鉴权和数据保护方案是什么？有无合规要求（隐私政策/审计）？

### F3 🟡 核心实体状态 / 生命周期未定义 [Clarify state transitions]
- 判定：方案引入有状态的实体（订单、审批、工单、消息），但无状态流转说明（创建后经过哪些状态、异常态如何回退）。
- 请回答：该实体的完整状态流转是什么？卡住/失败时停在哪个状态、谁能处理？

### F4 外部依赖与失败模式未声明 [Clarify integration / OpenSpec Impact]
- 判定（🟡）：方案依赖其他团队/系统/第三方服务，但未声明依赖方、接口假设和对方失败时的降级行为。
- 判定（🔴，校准 SEV：硬伤）：**核心卖点依赖的外部条件在高频场景失效，且降级模式下核心价值丧失**。例：联网智能硬件断网后对话能力消失只剩预置内容（"没网变砖"）；SaaS 依赖的接口失败时主链路无替代。降级体验与产品核心价值之间不允许有断崖。
- 请回答：依赖谁的什么能力？对方不可用时本功能怎样降级？依赖方是否已知情确认？高频失败场景（断网/断供/限流）下，用户还能获得核心价值吗？

### F5 🟡 高风险改动无灰度 / 回滚方案 [PRFAQ release plan]
- 判定：改动触及现有核心流程（通知、支付、权限），但无灰度、开关或回滚安排。
- 请回答：出问题时怎么快速止损（开关/回滚）？先放多少量、观察什么指标再全量？

### D1 🔴 关键商业断言无出处 [校准 SEV：硬伤 / PRFAQ]
- 判定：市场规模、增速（CAGR）、细分市场容量、竞争格局、"用户强烈需求/普遍痛点"等关键商业断言以确定语气陈述，但全文无来源标注，也未显式声明为"待验证假设"。
- 说明：本规则**文档内即可判定**（有断言、无出处），无需接入外部数据源；立项/融资/对外评审场景中无出处的市场数字等于没有数字。
- 请回答：这个数字/论断来自哪份报告或哪次调研？如果是内部估算，是否显式标注为假设并给出验证计划？
- **校准 v1.4.0**：来源已在附录分级，但正文/结论仍以确定语气引用"待核实清单"中的单源数字时，按 🔵 提示证据分级贯穿正文（正文加 ※ 标注或降级为"单源估计"措辞）。
- **校准场景**：调研/可行性文档关键数字无报告出处；IoT 硬件 PRD v1.3 提升为 🔴 硬伤（同日志）。

## G. 决策归集与可行性（v1.2 新增，真实项目校准）

### G1 🟡/🔴 决策点散落、未归集到决策清单 [校准]
- 判定：正文出现"待评审/口径待确认/规则待确认/审批流待定/待第 N 周实测/待最终锁定"等标记（脚本 G1 规则自动检出候选行），但未在文首/文末的"待评审决策"清单中一一列出；或决策清单与正文措辞/数量对不上。
- 定级：默认 🟡；若该决策点卡在**主链路闸门**上（资金、库存锁库、状态流转、限单动作），升 🔴。
- 请回答：这个决策的选项、默认值、负责人、拍板时间点是什么？为什么没进决策清单？
- **校准场景**：SaaS/平台工程 PRD×3（3200+ 行）——正文十余处决策标记未归集进决策清单（calibration.md 2026-08-27）。

### G2 🔴 排期与工作量不自洽 / 关键路径排期缺失 [校准 / IEEE830]
- 判定（软件项目）：人日 ÷ 人数 与日历周期明显不符，且未给测试/联调/试点缓冲；或"全部必做、不分优先级"但无砍项/降级预案；或高概率风险（外部系统联调、人员到岗不足）在排期中无应对。
- 判定（硬件/实体产品，校准 SEV：硬伤）：**完全没有上市倒排期**，或排期漏掉固定周期的关键路径——认证检测（如 3C/产品安全，通常 1-2 个月）、开模/结构件、量产爬坡、渠道/节日窗口。
- 请回答：测试+联调+试点缓冲是几周？资源不足/联调滑期时，哪些功能先砍、触发条件是什么？（硬件）从样机到上市的认证、开模、量产倒排期是什么？卡在哪个节日窗口？
- **校准场景**：SaaS PRD 排期人日与日历不自洽、无砍项预案；IoT 硬件 PRD 无认证/开模/量产倒排期（同日志）。

### G3 🔴 状态机 / 跨系统动作不完备 [校准 / Clarify state transitions]
- 判定：状态图中的状态缺少异常出口或客户可见态说明；跨系统的非原子写（如 OMS 落库 → ERP 建单锁库）只定义了成功路径，未定义失败态、重试边界、降级口径，以及降级期间的数据口径与业务责任。
- 请回答：该状态失败后客户看到什么、能做什么、不能做什么？降级方案的数据口径是什么？超卖/错账的责任和回滚路径是什么？
- **校准场景**：SaaS PRD 中间层→ERP 建单锁库为非原子写，失败态与客户可见态缺失（同日志）。

## H. 调研与可行性文档（决策就绪度，v1.3.2 新增 / v1.4.0 增补 H5，真实项目校准）

> 适用体裁：市场调研、可行性评估、立项报告。判定问题不是"能否进研发"，而是"能否据此拍板立项"。

### H1 🔴 结论超前于论证 / 论据自相矛盾 [校准]
- 判定：推荐结论或风险定级缺乏证据支撑，甚至被同文档证据反驳——例：把文档中已定性为违规被罚的同类产品的包装话术列为自己的推荐合规范例；风险表把"不成立则项目不成立"的依赖标为低/中风险。监管合规类结论尤其不允许靠常识推断，必须有书面法务意见支撑。
- 请回答：这个结论的直接证据是什么？与文中相反证据如何和解？合规定性有无书面法务意见？
- **校准场景**：调研/可行性文档——推荐合规范例与文档自身证据冲突、风险定级先于法务结论（同日志）。

### H2 🔴 关键经济假设无推导 / 成本口径不全 [校准]
- 判定：转化率、复购率、续费率/流失率、LTV、盈亏平衡销量、研发投入等关键测算数字无来源、无推导，或隐含荒谬假设（如零流失）；类比对象与本项目不可比（跨品类、跨商业模式）；毛利只算 BOM 口径，未扣渠道扣点、营销投放、物流退货、IP/授权费、认证与开模 NRE。
- 请回答：每个关键假设的来源/推导是什么？类比对象为什么可比？全口径（含渠道/营销/授权/NRE）后的单台贡献利润和盈亏平衡量是多少？
- **修复后复查口径（校准 v1.4.0）**：关键假设已显式标注为假设、且给出回填/验证计划时，本条不再报 Blocker；残留问题按 🔵 提示——公式不可复算（代入自设数字对不上）、年期/口径不一致（如 LTV 按 5 年而成本按 3 年）、收入与毛利混算、比例假设跨档位不一致、章节交叉引用错误。
- **校准场景**：同上文档——跨品类类比、隐含零流失、BOM 口径毛利（同日志）。

### H3 🟡 市场缺口被默认为机会，无需求验证 [校准]
- 判定："价格带空白/无竞品"直接推导为机会，未回答"为什么现有玩家不填"，对付费意愿溢价无验证（无预售/众筹/小批量测试计划）。
- 请回答：缺口是无需求还是无人做？立项前用什么低成本方式验证付费意愿？
- **校准场景**：同上文档——价格带空白直接推导为机会、无付费意愿验证（同日志）。

### H4 🔴 生命线依赖信息空白 [校准 / F4 立项版]
- 判定：项目成立的前提条件（IP 授权范围与费用、关键资质/牌照、独家供应链、法务定性）在文档中只有提问没有答案，且风险定级与之不匹配。
