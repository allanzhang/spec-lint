# 报告格式

评审报告用中文输出，严格按以下结构。Blocker 全部是"请回答"式填空题。

**报告是 findings 表的人读视图**，不是另一份数据源。表由 `scripts/spec_lint.py scan` 产出，
报告从表渲染；表里的 `question` 字段就是下面「请回答」那一栏，`fingerprint` 是跨轮次对得上的把手。

```markdown
# Spec 评审报告：<文档标题>

## 摘要
- 🔴 <n> 项必须回答 · 🟡 <n> 项建议补充 · 🔵 <n> 项表述问题
- 结论：<一句话——当前是否具备进入研发评审的条件；如不具备，卡点是什么>

## 🔴 Blocker（开发/评审前必须回答）

### [<规则ID>] <一句话标题>
- **位置**：<章节名>（第 <行号> 行附近）
- **原文**：「<逐字引用，不得改写>」
- **问题**：<为什么这是问题，一两句话>
- **请回答**：<针对该规则的具体填空问题>   ← 表里的 question 字段，下一轮上游要问的就是这句
- **指纹**：`<rule_id>:<hash>`   ← 跨轮次引用同一条问题时用它

（每条 Blocker 重复上述结构）

## 🟡 Warning（建议补充）
（同上结构，逐条列出）

## 🔵 Nit（表述问题）
（同上结构，可适当精简，但原文引用不可省）

## 需人工确认（工具不确定，不算硬伤）
- <位置 + 疑点 + 为什么不确定>      ← 表里的 need_human 字段

---
*本次启用规则：<按 rules.json 的体裁过滤结果列出>。如要关闭某条，改项目里的 `.spec-lint.json`。*
```

## 撰写要求

1. **原文逐字引用**：每条 finding 的「原文」必须是文档中的原句，不得转述；找不到原句的质疑不允许上报。**工具已强制这一条**（`--semantic` 会核对 evidence，编造的直接拒收）。
2. **同类合并**：同一规则在多处触发，报告中合并为一条并列举 2-3 个典型原文，注明"全文共出现 n 处"。（表里保持逐条粒度，便于逐条豁免与轮次比对。）
3. **空分区不省略**：某一级别为零时显式写"无"。
4. **结论只谈就绪度**：结论判断"是否可进入研发评审"，不判断产品方向对错。
5. **语气**：对事不对人，质疑针对文档不针对作者；问题说透，但不堆砌正确的废话。
6. **驳回要留痕**：机械层给的候选若判定为误报，写进 `resolutions` 标记 `dismissed` 并给理由，
   **不要从报告里悄悄删掉**——那条记录就是校准日志里的 FP，规则靠它收敛。
   驳回条目不进报告正文，但计入表里的 `dismissed` 计数。

---

## Blocker 回应追踪表（要求闭环时输出）

评审后给作者回收回应并逐条定结论，把"请回答"变成可追踪的工作流：

| 规则ID | Blocker 摘要 | 作者回应（原文填空） | 复核结论（已补/驳回/降级） |
|---|---|---|---|
| B1 | 目标无度量主体 | 「……」 | 已补：见 §x（复核通过） |

循环模式（SKILL.md 5.6）下，本表**由工具自动生成**，不要手抄：

```bash
python3 scripts/spec_lint.py round --prev r1.json --current r2.json
```

它按指纹比对，输出「已解决 / 仍存在 / 新出现」，并判定是否收敛。
**收敛信号是本轮「新出现」为 0**；门禁通过是「无未解决 blocker」。
已显式豁免（waivers）的条目算已解决，不阻塞过门。
